Wealth Portfolio Tracker

A household shares a portfolio of stocks, crypto, real estate and cash. Each member is an Owner, Editor or Viewer. Holdings and profit are calculated from a ledger that is never edited. An AI assistant answers questions and proposes transactions, and market prices update on a schedule.

Stack: Laravel 13 (PHP 8.3), Inertia with React and TypeScript, MySQL 8.4, Laravel AI SDK with Gemini, CoinGecko, Pest.

1. Scope

I ranked the brief's five areas by what the evaluation weighs most: access control that can't be bypassed, and the quality of the agent integration.

AreaDecision
Data and permission modelingIn depth. The agent is only as safe as the model under it.
Embedded AI agentIn depth. Streaming chat, four tools, human approval of writes, an audit log.
Async and external dataSmall. A scheduled price sync from CoinGecko every 5 minutes.
Real-timePartly. Values refresh every 30 seconds by polling.
UI/UXThroughout. Inline form errors, loading and empty states, readable 403/404 pages, keyboard access.

Deferred on purpose:

  • presence and collaborative notes;
  • multi-currency;
  • automatic cash movements on trades;
  • trading fees;
  • database row-level security and triggers.

Each one costs real time and isn't graded, and each is listed in section 7.

The work was planned in tiers (model and dashboard → agent → prices → tests and polish → live updates), each ending in something that runs. If time had run out, it would have stopped at a clean line.

2. Design

The core idea: every write goes through an Action class, and the Action checks permissions itself, on its first line, with Gate::forUser($user)->authorize(...). The web form, the AI agent and the tests are three ways in to the same Actions, so none of them can skip a check.

Each Action:

  1. checks permissions;
  2. locks the portfolio row inside a database transaction;
  3. enforces the business rules;
  4. writes the row.

A failure rolls everything back.

Five rules, each enforced in one place and each with a named test:

Rule
R1Only the price sync can set the price of a market asset (BTC, ETH, AAPL)
R2Only an Editor or Owner can value a private asset (a flat, a bank account)
R3A transaction can only use a market asset or one of its own portfolio's assets
R4A position can never go negative, at any point in time, including backdated sales
R5Ledger rows are never edited or deleted. Mistakes are fixed with a reversing row.

Roles:

ViewerEditorOwner
See everything, ask the assistantyesyesyes
Log or reverse transactions, value private assetsnoyesyes
Manage members, delete the portfoliononoyes

Money is stored as DECIMAL(24,8) and calculated as exact decimal strings, never floats. Profit uses average cost and is split into realized (sales) and unrealized (still held).

3. The AI assistant

ToolForDoes
get_portfolio_summaryall membersHoldings, value, cost, profit
get_allocationall membersWeights by asset and type, used for rebalancing suggestions
list_transactionsall membersRecent ledger rows
log_transactionEditor, OwnerProposes a trade, which the user must approve

How it stays within the user's permissions:

  1. Identity comes from the server. The user and the portfolio come from the session and the URL. No tool accepts a user or portfolio id, so the model can't choose who it acts as.
  2. One execution path. Every tool runs through AssistantTools::execute(). It checks permissions, calls the same services and Actions as the web, writes an audit row (agent_runs), and returns JSON. It never throws.
  3. A human approves every write. log_transaction pauses and shows an Approve/Reject card. On approval, the role, the conversation's ownership and a 10-minute expiry are checked again. Then the same LogTransaction Action runs and checks the role once more.
  4. The Action is the boundary. The tool list is filtered by role, but that's a courtesy, not the security. A Viewer who reaches log_transaction is refused by the Action, and the refusal is audited.

Replies stream as Server-Sent Events. Every refusal (403, 404, 422, 503) is sent before the stream starts, while the status code can still change.

4. Discussions: the choices that weren't obvious

QuestionOptions weighedDecision and why
Where should permissions be enforced?Route middleware, controllers, Form Requests, or inside the ActionsInside the Actions. The agent never passes through a controller or a route, so a check at the HTTP layer would leave it unguarded. In the Action, every entry point passes the same check.
Is a separate API tier needed (Express or REST)?Express or a REST API with a separate SPA, or InertiaInertia, no API tier. One server, session login, no tokens or CORS, and validation errors go straight to the forms. A separate API would have nothing to do. Cost: no ready-made API for a mobile app.
Which data layer?PostgreSQL (row-level security), MySQL, SQLite for testsMySQL with Eloquent. Exact decimals and the same transactions and locks. Without row-level security, authorization is concentrated in the Actions. The schema uses Laravel's builder only, so moving to PostgreSQL is a config change. SQLite was rejected for tests because it turned decimals into floats.
Which AI framework?Laravel AI SDK, Prism, Vercel AI SDK, a hand-written loopLaravel AI SDK. Tool calling, streaming, stored conversations, tool approval and test fakes in one first-party package. Prism would need approval and storage built by hand, and the Vercel SDK would need a Node server.
Should the agent write directly?Immediate writes, a read-only agent, or writes after approvalWrites after a human click, expiring after 10 minutes. It keeps the agent useful, and no write can happen even if the model is manipulated by text in the data (prompt injection).
Where does chat history live?Sent by the browser each time, or stored on the serverOn the server. The browser can't forge history. Reading the SDK's source showed it doesn't check who owns a conversation, so each conversation is bound to one user and one portfolio.
Which price provider?freecryptoapi.com (crypto only), Finnhub (stocks only), CoinGeckoCoinGecko, one provider for crypto and AAPL (through Apple xStock, a token that tracks the share). The free quota is 10,000 calls a month, so a 5-minute sync (about 8,640 calls) fits and a 1-minute sync wouldn't.
Live updates: push or poll?WebSockets (Laravel Reverb), or pollingPolling every 30 seconds. Prices change every 5 minutes, so the poll is already faster than the data. Reverb would add a server, a queue and a second auth path for no visible gain. It becomes the right choice for presence or second-by-second data.
What price does a transaction record?Force the market price, or let the user enter itUser-entered, pre-filled with the latest price. The market price values the portfolio, while the transaction price records what was actually paid. Trades can be backdated, and exchanges charge their own price.
Should fees be tracked?Keep a fee column, or drop itDropped. The brief doesn't ask for fees. Adding them back later is one column.
What does "profit" mean after a sale?Unrealized only, or realized plus unrealizedBoth, shown separately. With unrealized only, a profitable sale made the total profit drop. Reversed trades are left out of the calculation entirely, so a corrected mistake leaves no trace.
What if the AI provider is overloaded?Show the error, retry the same model, or fail overFail over to a second Gemini model. Google's 503 "overloaded" errors are per model. The fallback is set in config.
Database triggers for R5?Triggers, or app-level guards onlyApp-level for now. Model guards, no update or delete routes, and an architecture test. Triggers are the next step.

Every decision, with its cost, is in docs/decisions.md.

5. Type safety across PHP and TypeScript

The contract is checked at each boundary:

  1. Form Requests validate the input.
  2. A typed DTO and PHP enums carry it into the Actions.
  3. Hand-written TypeScript types describe each page's data, with no any.
  4. assertInertia tests pin what the server actually sends, so the types can't drift.

6. How I used AI tools

  1. Plan first. A build guide and four task lists (database, Actions, HTTP and UI, agent), each task with "done when" checks.
  2. One task at a time. Claude Code executed a task, then reported what changed, why, how it was verified, and any open questions. I reviewed it and made the decisions before the next task.
  3. Read the source, don't guess. The SDK findings above, the ownership gap and a hidden extra model call per chat, came from reading the installed code.
  4. Verify, don't trust. Tests, the type check and the build ran after every task. For key protections I broke the code on purpose to confirm a test fails.

The review caught real problems:

  • The tables were created with a storage engine that silently ignores transactions.
  • The test database turned money into floats.
  • The SDK trusts any conversation id.

Tests: 400 Pest tests on MySQL, none of which touch the network:

  • every rule, in both its allowed and refused case;
  • every write endpoint, against guests, non-members and Viewers;
  • 125 tests for the agent.
