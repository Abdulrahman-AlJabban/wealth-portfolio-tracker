Project guide

Wealth Portfolio Tracker

A shared investment ledger. Family members and partners track holdings, cost basis and profit in one portfolio, each with a role, and an AI assistant can answer questions and propose trades that a person approves.

394 tests passing 5 domain rules (R1 to R5) 3 roles money stored as DECIMAL(24,8) smallest unit 0.00000001

01Overview

The app tracks portfolios. Each portfolio has members with a role (Owner, Editor or Viewer), a ledger of transactions (buy, sell, deposit, withdrawal), and assets: global market assets such as BTC, ETH and AAPL, and private assets such as a flat or a bank account that only that portfolio can see.

Positions, cost and profit are never stored. They are computed from the ledger every time, using the average-cost method. Corrections are made by adding a reversing row; ledger rows are never edited or deleted.

Stack

  • Laravel 13 on PHP 8.3, MySQL 8.4 (InnoDB)
  • Inertia v2 with React 18 and TypeScript, Tailwind
  • Breeze for authentication
  • Pest 4 for tests, Pint for formatting
  • Laravel AI SDK (laravel/ai 1.3) with Google AI Studio (Gemini)

Built in four phases

  • Database layer: tables, enums, models, seed data
  • Policy and Actions: the write path and rules R1 to R5
  • HTTP and UI: controllers, routes, React pages
  • AI assistant: tools, streaming chat, approvals

Each phase has a task list and a dropoff report in docs/ and the project root.

02Run it

  1. Install dependencies. composer install and npm install.
  2. Configure the environment. Copy .env.example to .env, run php artisan key:generate, and point DB_* at a MySQL database named wealth.
  3. Create the database and demo data. php artisan migrate:fresh --seed.
  4. Start the app in separate terminals: PHP_CLI_SERVER_WORKERS=4 php artisan serve and npm run dev. More than one PHP worker is needed because the assistant streams its answers.
  5. Log in at http://127.0.0.1:8000 with one of the demo users below. The password is password.
UserRole in "Family wealth"Use it to show
alice@example.comOwnerEverything, including members and deleting the portfolio
bob@example.comEditorLogging and reversing transactions, valuing private assets
carol@example.comViewerRead-only access; she also owns "Carol personal" for isolation tests

The seed data creates the global assets BTC, ETH and AAPL with one market price each, the private asset "Damascus flat" with a manual valuation, and four buys. The seeded portfolio is worth 132,600.00 against a cost of 124,100.00, a profit of +8,500.00.

Two local MySQL facts. The local server's default storage engine is MyISAM, which silently ignores transactions, row locks and foreign keys; config/database.php forces InnoDB, so never remove that. Tests run on a separate database, wealth_test, set only in phpunit.xml. There is no .env.testing, so php artisan ... --env=testing still targets the dev database.

To turn on the assistant, add a Google AI Studio key to .env; see section 11. Without one, the assistant panel says "not configured" and the rest of the app works.

03Design principles

Each principle below shows up as a concrete rule in the code and is checked by a test.

All writes go through Actions

Controllers and assistant tools never create, update or delete models. They call an Action, which authorizes the user, checks the domain rules and writes inside a database transaction. An architecture test fails the build if a controller or agent file writes directly.

Every Action authorizes itself

The first statement of each Action is Gate::forUser($user)->authorize(...). Nothing relies on the caller having checked, because the assistant never goes through a controller.

Money is a decimal string

Amounts and quantities travel as strings from the form to bcmath to DECIMAL(24,8). No float is used anywhere. The UI only formats strings for display and never does arithmetic on money.

The ledger is append-only

Positions are derived, never stored, so there is no balance to drift. A mistake is corrected with a reversing row that points at the original through reverses_id.

The database catches duplicates, the code catches rules

Unique indexes and foreign keys stop duplicates and orphans. Business rules such as "no negative position" live in the Actions, where they can give a clear error.

Identity comes from the server

The user always comes from the session and the portfolio from the route. Neither forms nor the AI model can supply a user id or a portfolio id.

Defense in depth

Hiding a button, filtering the assistant's tool list, and policy checks are separate layers. The Action check is the real boundary; the others make mistakes less likely.

Portable schema

Migrations use the schema builder only, no MySQL-specific SQL and no ENUM columns. Allowed values live in PHP enums, so moving to PostgreSQL is a config change.

06Rules R1 to R5

The five rules are the contract of the ledger. Each has one named test in tests/Feature/RulesTest.php.

RuleStatementEnforced inProven by
R1A global market asset is priced only by the price sync, never by a user.SetAssetPrice refuses global assets; the valuation route only resolves private assetsr1_users_cannot_price_global_assets
R2A private asset is valued only by an Editor or Owner of the portfolio that owns it.SetAssetPrice (Gate plus owner portfolio check)r2_viewer_cannot_value_private_asset
R3A transaction's asset is global or belongs to the same portfolio.LogTransaction looks the asset up through usableAssets(); a missing or foreign asset gets the same messager3_cannot_log_against_other_portfolios_asset
R4A position is never negative at any point in time.PositionService::assertNeverNegative() replays the ledger in date order after the insert, under a portfolio row lock; a failure rolls the insert backr4_cannot_oversell, r4_cannot_oversell_with_a_backdated_sell
R5Ledger rows are never updated or deleted.No edit or delete routes, model guards on Transaction, unique reverses_id, soft-deleted portfoliosr5_ledger_is_append_only

Why R4 replays the ledger. Comparing a sell against today's total would let a sell dated last week pass even if nothing was held last week. Replaying in date order catches it.

Known R5 gap. A query-builder update (Transaction::whereKey(...)->update(...)) bypasses the model guard. The optional database triggers that would close it were not built; the test r5_known_gap_query_builder_update_bypasses_model_guard documents this.

09Valuation

ValuationService::summary() is the one place that turns the ledger into numbers. The dashboard and the assistant both use it, so they cannot disagree. It runs three queries however many assets are held: transactions, assets, and their latest prices.

  • Inflows (buy, deposit) add quantity × price to cost and add the quantity.
  • Outflows (sell, withdrawal) remove the average cost of what left.
  • Assets with zero quantity are left out. An asset with no price is valued at 0 and shows "No price yet".
  • total_pnl is computed on the server, so the browser never subtracts money.

Example: buy 2 at 100, buy 2 at 200, sell 1. Average cost is 150, so quantity is 3.00000000 and cost is 450.00000000.

allocation() builds weights by asset and by type from summary(). Weights are rounded half-up to 2 decimals, which keeps their sum within 0.01 of 100. For the seed data: flat 64.10%, BTC 24.51%, ETH 9.65%, AAPL 1.73%.

10Use cases

Log a transaction (the most important path)

  1. Form. An Editor fills the Transactions tab. Amounts are text inputs, never number inputs. The form sends a fresh idempotency_key so a double click logs once, and the optional date as an ISO UTC timestamp.
  2. Route. POST portfolios/{portfolio}/transactions, behind auth.
  3. Form Request. LogTransactionRequest checks the shape and builds LogTransactionData.
  4. Action: authorize. LogTransaction checks write first; a Viewer gets 403.
  5. Action: validate. Quantity positive with at most 8 decimals, price non-negative, date not in the future.
  6. Action: lock and check. Inside a transaction: lock the portfolio row, look up the idempotency key, apply R3 and the single-currency rule.
  7. Action: write and verify. Insert the row, then for a sell or withdrawal replay the ledger (R4). A failure rolls the insert back.
  8. Response. Redirect back with "Transaction logged." or with the error under the right field.

11AI assistant

The model is a brain with no hands. It can only ask for a tool to be run. Our code runs the tool, checks permissions, and returns the result as JSON. The model never touches the database.

Approving a write

  1. The user asks "Log a buy of 0.1 BTC at 65000". The model calls log_transaction, but the SDK pauses the run. Nothing is written.
  2. The stream sends an approval event. The panel shows a card with portfolio, asset, type, quantity and unit price, and Approve and Reject buttons.
  3. POST …/agent/approvals checks, before streaming: the user can still write (403), the conversation is theirs in this portfolio (404), and the request is still pending and less than 10 minutes old (422).
  4. On Approve the SDK resumes and runs the tool as that user, through LogTransaction, which checks the role again. The new row has source = agent and an Agent badge.

Security points

  • No identity from the model. No tool parameter is a user or portfolio id.
  • Role filtering is not the boundary. A Viewer calling log_transaction directly is refused by the Action and the refusal is audited.
  • Server-side history. Forged messages, role or user_id fields in the request are ignored.
  • Prompt injection. Names from the database only appear as JSON string values; the instructions say tool results are data; a write still needs a human click.
  • No leaks. Provider errors become "The assistant is unavailable right now."; the real error is reported in the logs.
  • Money as strings. A quantity sent as a JSON number is refused with a clear message instead of passing through a float.

How the tests were checked

  • Mutation checks. For key protections the code was broken on purpose to confirm a test fails: removing eager loading, the portfolio scope on conversations, the stale-role check on members, the rounding of weights, and moving the 403 inside the stream.
  • Assistant tests use the SDK's fakes. A scripted tool call runs our real tools with no network.
  • Approvals use the real SDK path. The SDK skips approved tools when an agent is faked, so those tests drop the fake: the SDK runs the tool, then its model call is blocked by the network guard.

15Decisions and fixes

Main decisions

  • MySQL over PostgreSQL. Exact DECIMAL and the same transaction behaviour. The cost is no row-level security, so authorization is in the app and tested per rule.
  • Laravel with Inertia, no separate API. One server, session auth, no CORS or tokens.
  • Global and private assets in one table through a nullable portfolio_id: one price serves every portfolio, private assets stay isolated.
  • The assistant calls Actions, not models, so the user's role binds it automatically.
  • Human approval for agent writes, so a model can never change data on its own.

16Known gaps

Ledger and data

  • Query-builder updates bypass the R5 model guard (triggers not built)
  • Single currency: market assets are USD, so other-currency portfolios hold only private assets
  • Average-cost accounting only; trading fees are not tracked
  • Cash is not debited on buys
  • Market prices refresh every 5 minutes (free CoinGecko quota); AAPL is priced through Apple xStock, a tokenized stand-in
  • No concurrency test; locks are reasoned about, not run in parallel

UI

  • Transaction list shows the latest 50, no pagination
  • Live prices by polling every 30 s, not push; no collaborative realtime (presence, notes); no dark mode in the app
  • No confirm before an owner demotes themselves

Assistant

  • No token or cost budget, only 20 messages a minute
  • No offline evaluation of prompt quality
  • One provider and model tested
  • A page refresh starts a new chat; old conversations cannot be reopened
  • Replies are plain text; Markdown shows as raw characters
  • The SDK replays up to 100 messages, so long chats cost more
